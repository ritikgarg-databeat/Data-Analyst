# Backup & Restore

Phase 12 added the platform's first backup/restore system — before it, the only "export" mechanisms
anywhere were four scoped, client-side CSV/JSON/text Blob downloads (SQL results, a DataFrame preview,
a Python notebook's code, and the Career Report), none of which could restore anything.

## What's backed up

Every row that's genuinely *yours* — lesson progress, exercise/assessment attempts, projects
(including milestones/artifacts/dataset links), case attempts, interview notes/bookmarks, your career
profile/target roles/goals/milestones/assessments/behavioral stories/achievements, saved job
descriptions (with extracted requirements/analyses/skill gaps/prep workspaces), resumes (with every
version/evidence/review), your portfolio, AI settings/conversations/mistake-memory/skill-diagnoses.

See `apps/api/app/services/backup_service.py`'s `ENTITIES` list for the exact, current table list —
that list *is* the authoritative scope, kept in one place rather than duplicated here.

## What's deliberately NOT backed up

- **Secrets.** No API key, database credential, or anything from `.env` is ever included — those stay
  in your environment, not in a backup file.
- **Imported dataset files.** A `Project.dataset_id` in a restored backup may point at a dataset the
  target environment hasn't re-imported. This is safe (SQLite's foreign-key enforcement isn't enabled
  in this app, so a dangling reference doesn't break restore) but the dataset itself won't resolve to
  real data until you re-import it by hand via the Dataset Hub.
- **Generated warehouse/dbt artifacts** (`data/warehouse/*.duckdb`, `dbt/target/`) — these are
  regenerated by re-running `dbt build`, not meaningfully "restorable" as data.
- **Platform content** (lessons/exercises/cases/skills/role templates/achievements) — that's seeded
  from `content/**/*.yaml` and `database/seeds/*.yaml`, the same on every install; backing it up would
  just duplicate what `make seed` already produces.

## How to back up

```bash
make backup
# or, without needing the API server running:
uv run --project apps/api python -m app.db.backup_cli
```

Writes a timestamped JSON file to `data/backups/backup-<timestamp>.json`. The same bundle is also
available live via `GET /api/v1/platform/backup` if you're scripting against a running server.

## How to restore

```bash
make restore FILE=data/backups/backup-20260101T000000Z.json          # dry run — always safe
make restore FILE=data/backups/backup-20260101T000000Z.json YES=1    # actually applies it
```

Restore always previews first (manifest, row counts, any compatibility issues) and requires an
explicit confirmation before writing anything — never destructive by default. It's also **idempotent
by primary key**: a row whose id already exists in the target database is left untouched, never
overwritten, so re-running a restore (e.g. after a partial failure, or just to "top up" a database that
already has some of the data) is always safe and never duplicates anything.

The one exception is your three singleton settings/profile rows (AI Settings, Career Profile,
Portfolio) — each is lazily created the first time you touch that feature, so by the time you restore
an old backup you may already have one under a different id. For these three only, restore matches by
your user id instead and updates that row's fields from the backup, rather than skipping it (which
would otherwise leave a placeholder default in place forever) or inserting a duplicate (which would
crash on that table's own uniqueness constraint). Every other table stays purely additive.

## Verified round-trip

This isn't a theoretical design — during Phase 12 it was tested end to end: export a real backup,
delete several rows across five different tables, restore the backup, confirm the deleted rows come
back with their original ids, then restore the *same* backup again and confirm zero duplicate rows are
created the second time.
